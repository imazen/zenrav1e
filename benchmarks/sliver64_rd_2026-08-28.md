# TX_64X16 / TX_16X64: real 64-dim sliver transforms vs the 3fa735dc cap

**Question (zenrav1e#28, the last two open items of its "done means"):** with
`BLOCK_64X16` / `BLOCK_16X64` now coding their real max rect transform,
(a) do those streams round-trip conforming decoders on a real-image corpus,
and (b) what is the RD delta against the `rdo_tx_size_type` cap that used to
force them down to `TX_32X16` / `TX_16X32`?

**Verdict:** the real transforms are **RD-neutral-to-slightly-better and not
slower** — mean BD-rate(Y) **−0.076 %** over 47 corpus cells (−0.084 % over the
43 where a sliver block was actually placed), best cell −0.83 %, worst +0.39 %,
total coded bytes −0.034 % at matched quantizer. Encode time over a controlled
serial A/B is **−1.4 %** (i.e. slightly faster), with per-cell swings from
−15.3 % to +7.1 %. So the fix's
value is **correctness, not compression**: it removes a path that could emit
streams no decoder accepts, and with it the partition gate — it does not buy
meaningful bitrate. Nothing argues for turning the 4-way-at-64x64 partition on
in a stock preset on RD grounds; nothing argues for restoring the cap either.

Decode conformance on the same corpus: **141 / 141 streams**, under aomdec (aom
3.14.1), dav1d 1.5.4 *and* rav1d-safe, each decoding **byte-identically to the
encoder's own reconstruction**; 73 of those 141 cells place sliver blocks,
across all four image sizes.

## Arms

| Arm | Commit | Behaviour |
|-----|--------|-----------|
| A (test) | `2c599311` (master, 2026-08-28) | sliver blocks code `TX_64X16` / `TX_16X64` |
| B (baseline) | `064c62e9` (= `e4883037^`) | the 3fa735dc cap: intra sliver TX forced one level down, tx-size depth walk shortened to 1, `sliver_tx_safe` partition gate present |

Arm B is the encoder as it stood immediately before the fix, built from
`git archive e4883037^` into a scratch tree with `examples/sliver64_rd.rs`
dropped in (its `[dev-dependencies]` sections were stripped so the scratch
build does not pull the test-only decoders; nothing else was changed).
Building the real old encoder is the only honest baseline — the cap was
decoder-followable **only** under `TX_MODE_SELECT`, so re-applying it on
today's tree would mean restoring the old `tx_mode_select` plumbing and the
partition gate too.

Between `e4883037^` and master the only behaviour change a **still, intra-only**
encode can see is `e4883037` itself (the other commits fix inter-frame `has_tr`
/ sub-8x8 chroma prediction, or add tests). The data confirms it: of the 423
(image, quantizer) rows, **206 place no sliver block in either arm, and all 206
are byte-identical and PSNR-identical**. 226 rows in total are identical.

## Configuration

No stock preset can reach a 64x64-parent 4-way partition, so the stock RD delta
is exactly zero — which is why `gate_identity`'s pins did not move. Presets 0/1
keep `non_square_partition_max_threshold` at `BLOCK_64X64` but are **bottom-up**,
and only `encode_partition_topdown` offers `PARTITION_HORZ_4` / `VERT_4`;
presets 2+ are top-down but cap that threshold at `BLOCK_8X8`. The measurable
configuration is the one zenavif/ravif reach by widening the partition knobs
(`deep` in the harness):

- `SpeedSettings::from_preset(2)` with
- `partition.encode_bottomup = false`
- `partition.partition_range = BLOCK_4X4 ..= BLOCK_64X64`
- `partition.non_square_partition_max_threshold = BLOCK_64X64`
- `still_picture`, 8-bit, 4:2:0, `with_threads(1)`, `quantizer == min_quantizer`

Speed 2 also keeps `rdo_tx_decision = true` (`TX_MODE_SELECT`), which arm B
needs to express its cap at all; speeds ≥ 6 turn it off, and there the old
encoder withheld the partition candidates entirely rather than capping.

## Corpus and grid

47 cells = 15 images × a size ladder, all **center crops of the source pixels**
(no resampling, no upscaling):

| Class | Source | Sizes |
|---|---|---|
| photo | clic2025 training (6 images) | 128, 256, 512, and 1024 for 3 of them |
| photo | CID22-512 training (4 images) | 128, 256, 512 |
| photo | gb82 `city`/`flowers` | 128, 256, 512 |
| screen / line-art | gb82-sc `graph`, `gui`, `codec_wiki` | 128, 256 (+512 where the source allows) |

Quantizer sweep: **30, 55, 80, 105, 130, 155, 180, 205, 230** (9 points,
uniform across the range, i.e. the low-quality half is sampled as densely as
the high-quality half). 423 encodes per arm. Distortion is PSNR of the encoder
reconstruction against the source YUV; BD-rate is the standard Bjontegaard
cubic fit of log10(bytes) over PSNR, per cell
(`benchmarks/bdrate.py armB.tsv armA.tsv psnr_y`).

Raw per-cell data: `sliver64_rd_armA_2026-08-28.tsv`,
`sliver64_rd_armB_2026-08-28.tsv` (the derived `bpp` and `psnr_avg` columns are
dropped; `bdrate.py` recomputes the 6:1:1 average on demand).

## Results

### BD-rate, arm A vs arm B (negative = master needs fewer bits)

| Slice | n | mean BD-rate(Y) |
|---|---|---|
| all cells | 47 | **−0.076 %** |
| cells where a sliver block was placed in either arm | 43 | −0.084 % |
| 128px | 15 | −0.076 % |
| 256px | 15 | −0.021 % |
| 512px | 14 | −0.125 % |
| 1024px | 3 | −0.125 % |
| photo | 39 | −0.086 % |
| screen / line-art | 8 | −0.028 % |

Spread is wider than the mean: best `clic2_512` −0.829 %, worst `sc1_256`
+0.390 %. On the 6:1:1 luma/chroma PSNR average the mean is −0.046 %.

Aggregate over all 423 rows at matched quantizer: coded bytes **−0.034 %**,
mean ΔPSNR(Y) **+0.008 dB**. Both point the same way as the BD-rate and are of
the same (negligible) magnitude.

### What the encoder does differently

Sliver **pixels** placed across the grid rise from 1,480,192 (arm B) to
4,730,112 (arm A) — 3.2×. The capped arm still *chooses* `BLOCK_64X16` /
`BLOCK_16X64` partitions, it just codes them with a split transform; making
the 64-dim transform available makes those partitions win the RD comparison
far more often. That the resulting rate/quality barely moves is the finding:
the two codings of the same partition are near-equivalent.

### Encode time

Serial A/B/A/B on 6 cells × 4 quantizers (one process at a time, `nice -n 19`,
no other load), two runs per arm: `sliver64_rd_time_2026-08-28.tsv`. The
measurement is tight — within-arm run-to-run totals differ by 0.02 % (A) and
0.11 % (B) — so the between-arm number is real, not noise:

| | arm A | arm B | delta |
|---|---|---|---|
| sum of per-cell min-of-2 | 172.4 s | 174.7 s | **−1.32 %** |
| sum of both runs | 345.0 s | 349.9 s | −1.39 % |

Per cell it ranges from −15.3 % (`cid1_512` q205) to +7.1 % (`sc2_256` q205).
Arm A evaluates one *more* transform-size depth per sliver block (its walk
starts at `TX_64X16` instead of `TX_32X16`) yet comes out slightly ahead,
because choosing a sliver partition with its own transform ends the search
that the capped arm continues into deeper splits. There is no encode-time
argument for the cap.

(The 47-cell sweep's own `ms` columns — 3955.2 s vs 3948.1 s, −0.18 % — were
collected 4-way sharded under varying load and are not a controlled timing
measurement; they are consistent in sign with the serial numbers.)

### Decode conformance on the corpus

`SLIVER64_RD_DUMP` on the same 47 images at q80 / q130 / q205 wrote 141 IVF +
reconstruction pairs; `scripts/sliver64_corpus_decode.sh` (also
`just gate-sliver64-corpus <manifest>`) required each to decode under **aomdec
(aom 3.14.1)**, **dav1d 1.5.4** and **rav1d-safe** (via zenavif's `ivf_raw`
example, the `IVF_RAW` leg `gate_recon.sh` already uses) and to match the
encoder's reconstruction byte-for-byte: **141 ok, 0 failed**, with 73 cells
placing sliver blocks (1,610,496 sliver pixels; live at 128, 256, 512 and
1024). Per-cell data: `sliver64_rd_decode_2026-08-28.tsv`.

The gate is mutation-verified: flipping one bit in a stream's payload gives
`aomdec-reject`, and flipping one byte in the reference reconstruction gives
`aomdec-mismatch`. A decoder that merely *accepts* the stream is not enough —
the encoder must have optimized against the reconstruction a decoder actually
produces, which is why the comparison is byte-exact rather than "decodes".

## Host and build

Apple M-series (aarch64), macOS 26.5.2, rustc 1.98.0, `--release`, default
features (`threading`), **no** `-C target-cpu=native`. Both arms built with the
same toolchain and flags.

## Reproducing

```sh
# corpus -> raw RGB + manifest (center crops, no resampling)
#   magick <src>.png -crop <S>x<S>+<ox>+<oy> +repage -depth 8 rgb:<name>_<S>.rgb
#   manifest rows: <name>\t<path.rgb>\t<w>\t<h>
cargo build --release --example sliver64_rd
./target/release/examples/sliver64_rd manifest.tsv 2 30,55,80,105,130,155,180,205,230 deep > armA.tsv

# arm B: git archive e4883037^ into a scratch dir, drop in the same example,
# strip [dev-dependencies], build, run the identical command
python3 benchmarks/bdrate.py armB.tsv armA.tsv psnr_y

# decode conformance over the same corpus
just gate-sliver64-corpus manifest.tsv
```
